# 用户参与的帖子反馈

## 功能与边界

桌面和移动帖子的「👍 有用」「👎 没帮助」是 Daily Feed 内部标记。两者互斥，再次点击同一个按钮取消，可从赞直接切换为踩。不会调用 X 的点赞/转发接口，不改变收藏、已读或抓取排序，也不消耗 X 抓取积分或翻译额度。

本次交付是反馈采集、统计和数据导出，供随后用真实样本评估筛选规则。没有用少量反馈自动训练模型或改变所有人的排序；未标记绝不能作为负样本。点赞/点踩也无法区分“不相关”和“内容质量差”，分析时应保留这个局限，后续可增加可选原因。

功能随 0.11.0 发布。线上 Worker、移动入口与桌面客户端需要配套部署；旧客户端需安装新版后才能显示反馈按钮。部署与验收步骤见本文末尾。

## 现有架构补充了什么

继续使用原有 Cloudflare Worker 和账号账本，不增加外部账号服务或 AI 服务。

1. `FeedbackDO`：独立 SQLite Durable Object，存当前标记和不可变修改历史。通过 `FEEDBACK` 绑定和 `v4-feedback` 迁移创建，不改动账号余额表。
2. 认证接口：提交和读取本人反馈。账号身份来自账本，客户端提交的账号/角色字段不参与权限判断。内测、普通、超管均可反馈，普通用户余额为零也能使用；停用账号不能访问。
3. 本机待传队列：桌面 SQLite `state` 和移动 IndexedDB 中按登录账号分区存放。先持久化，再请求后端。离线显示「待同步」，重新打开列表、联网或点「重试同步」后重传。
4. 管理接口与导出：仅 `ADMIN_TOKEN` 可访问全局统计与 JSONL 数据；桌面安装包和移动端不包含这个密钥。

生产和预发的 Worker/DO/账号独立，本地 test/staging 的数据库也独立。`dev/deploy-staging.mjs` 会向生成的预发配置补齐独立反馈绑定及迁移。代码、配置模板、测试和本说明随完整源码一并发布；数据库、反馈导出文件和密钥不进 Git。

## 记录的数据

每次实际修改保存：

- 帖子 ID、原始抓取帖 ID（转推统一关联到原帖）、作者、文字及一层引用。
- 链接、图片数量、链接卡片标记、当时的 X 点赞/转发/回复/浏览量、发布时刻和抓取来源。
- 反馈值 `1 / -1 / 0`、之前的值、服务端时间、修订版本和事件编号。
- 客户端平台、版本、列表视图、排序、列表位置、算法版本 `baseline-v1`。
- 服务端计算的正文、引用与链接内容 SHA-256（排除变化的互动量和来源字段） 和 `content-v1` 内容特征（文字长度、引用长度、链接数等）。

这些是用户反馈时由客户端提交的快照，`provenance=client_reported`，没有重新调用 X 验真。正文/引用各最多保留 50000 个 UTF-16 字符，超长明确标 `truncated`，不静默当作全文。不会上传整个本地数据库、私有 API Key、关注列表或未反馈的帖子正文。

研究数据使用账本内部不透明 ID 作为 `user_key`，不保存或导出可直接用于登录的 DF 短编号和明文凭据。这属于去标识化，并非无法关联到个人：运营者仍能通过受保护的账号账本关联内部 ID，因此导出仅供管理端。

## 计数、一致性与离线

- `feedback_current` 主键是 `(user_key,post_id)`：每人每帖当前只计一次。
- `feedback_events` 记录修改历史。改变方向/取消各产生一次修改，不能把历史赞数简单相加当作当前赞数。
- 待传事件有稳定 UUID。服务端已经保存、但响应丢失时，客户端重启后仍用同一 UUID 重试，服务端不重复计数。
- 采用服务端修订号处理多设备冲突。旧设备的请求遇到新修订会读回当前标记并提示重新选择，不自动覆盖。
- 离线标记写入本机成功后才显示待传；本机写入失败不会向后端发送。待传期间该帖不能继续切换，但可以重试。其他帖子和阅读操作不受影响。
- 每账号每天最多 2000 次实际修改（UTC 日期），幂等重传不计入；请求体和读取数量有限制。
- 取消会让当前标记归零，历史事件仍保留。构造训练样本应取同一用户/帖子的最新状态，排除最新值为零的记录。
- 同账号其他设备只同步反馈标记，不同步其本地帖子、收藏、已读或关注设置；新设备需先获得同一帖子才会展示相同标记。

## API

| 接口 | 权限 | 用途 |
|---|---|---|
| `POST /v1/feedback` | 有效账号 | `{event_id,value,expected_revision,snapshot,context}` |
| `POST /v1/feedback/read` | 有效账号 | `{ids:[帖子ID]}`，一次最多 200，只返回本人状态 |
| `GET /admin/feedback/stats` | 管理口令 | 当前有效赞/踩、参与人数、帖子数、历史修改次数及前 100 条反馈量较多的帖子 |
| `GET /admin/feedback/export` | 管理口令 | `kind=events|current`，`after`、`until`、`limit<=500` 分页 |

以上接口均 `Cache-Control: no-store`，移动入口只代理前两项，Service Worker 不缓存 API。管理接口不会代理到公开移动域名。

## 查看统计、导出研究数据

使用已有管理密钥配置，命令必须显式选择环境：

```sh
npm run relay:admin:staging -- feedback-stats
npm run relay:admin:staging -- feedback-export events
npm run relay:admin:production -- feedback-stats
npm run relay:admin:production -- feedback-export events
```

默认导出到 `.local/<环境>-feedback-events-<时间>.jsonl`，权限 0600，可在类型后指定新的输出路径，已有文件拒绝覆盖。导出失败会移除不完整文件。每行附 `schema_version`、环境、内容快照、特征和上下文；供 Python/表格/后续评估脚本使用。`events` 导出固定上限序号，分页时不会无限追赶新事件；`current` 是实时视图，多页导出时若用户持续修改，不能视为严格的同一时刻快照。

统计页中的赞/踩只代表主动反馈的人。当前未收集所有帖子的曝光，不能用这些数量计算全体满意率、点击率，或把高反馈量直接当成高质量。后续算法评估应按用户和时间留出验证样本，避免同一事件/同一内容同时进入调参集和验证集。

## 验收与上线

```sh
npm test
npm run test:ui
npm run test:mobile
```

测试覆盖真实 workerd/SQLite/RPC、三类账号、停用/未登录拒绝、他人状态不可读、幂等/并发/版本冲突、响应丢失、存储失败、服务重启、测试/预发隔离、CLI 实际导出，以及隐藏窗口中的真实桌面按钮/IPC和移动按钮/离线重启。

本地手工验收：`npm run dev`（桌面）或 `npm run mobile:dev`（浏览器），使用样例账号即可，不需要真实 X 或 Azure 密钥。自动化验收使用隐藏窗口，不启动正式应用。

发布时先部署并验证预发 Worker，再统一部署正式 Worker、移动入口和发布新版桌面包；新客户端遇到旧后端会保留待传标记并提示重试。账号/余额迁移保持原样，新增的 `v4-feedback` 仅创建反馈 DO。首次发布后用有效账号做一次标记、管理端核对和取消，确认真实服务链路。真机 Safari 的操作体验仍需设备验收。
